XRPBlocks: updates through 20 September 2026

This is the current addendum to changes 1-18 in the replication guide. It records the final implementation, including corrections made during testing. Earlier PDF pages are retained as historical documentation; this addendum takes precedence where behavior differs.

19. Onboard RGB colour and brightness

The Board category adds a named-colour dropdown with brightness from 0 to 100%. Eleven choices match the NeoPixel palette, including off. Default brightness is 30%. Generated Python clamps brightness and scales RGB values. It requires no NeoPixel add-on library. English and Dutch labels are available. The original three-channel RGB block remains available.

20. Delete unused blocks

Right-click the workspace or a block and choose Delete unused blocks. Cleanup removes disconnected stacks and unreachable functions. It preserves start blocks, explicitly protected blocks, and functions called directly or indirectly by retained code, including recursive calls. Default shadow inputs do not incorrectly protect a disconnected stack. Deletion is grouped for Undo. The option is disabled when there is nothing eligible to remove.

21. Bottom panel and variable cleanup

The whole Python/Console panel starts collapsed unless pinned. Both tabs offer a shared pin control, remembered in the browser. Unpinning hides the panel. Unpinned tabs open manually; Run and Deploy do not force them open. Clicking elsewhere no longer dismisses a manually opened panel. Resizing preserves the expanded size without overriding the collapsed height.

Variables with no references anywhere in the workspace are removed on app startup and before Run. References in loose blocks and procedure parameters are retained. Cleanup is grouped for Undo and the workspace is saved.

22. Remembered connection and uninterrupted startup

Connect first tries the last successful authorised USB or Bluetooth device. USB uses the exact in-session port when possible; after reload it matches USB vendor/product IDs only when a single authorised port matches. Missing, ambiguous or failed connections return to the chooser. Bluetooth reuse depends on browser support for previously authorised devices. Repeated Connect clicks are guarded while connection work is in progress.

Connect no longer sends a stop/REPL-recovery command. This preserves a web server or other main.py program already running on power-up. Stop remains available whenever connected. Run, Stop and Deploy can interrupt execution. Deploy saves main.py but does not run it: click Run or restart the board.

23. Mecanum wheels library, version 1.1.0

Four encoded motors drive standard X-pattern mecanum wheels. Default ports are 1 front-left, 2 front-right, 3 rear-left and 4 rear-right. The palette provides two compact setup blocks: motor assignment and chassis geometry. The older combined setup block remains registered for saved-project compatibility.

Controls include eight directions, arbitrary movement angle, continuous drive, distance in centimetres, turning in degrees, Stop, wheel reversal and a last-move-completed Boolean. Speed is 0-100% of configured maximum wheel RPM, not a guarantee of chassis speed. Distance and turns use encoder estimates, with timeouts and stopping on completion/interruption. Wheel diameter and wheelbase/track defaults are placeholders that must be measured and calibrated. Mecanum hardware operation has not been verified in this session.

24. Remote control library

Remote control is independent of motors and mecanum. Its MicroPython driver hosts an HTML page on port 80, either through a robot hotspot or by joining an existing network. The page has six customizable hold buttons, local label editing, connection status and Release all buttons. Blocks read held state, one-shot press events, connection status and page address, and configure labels, title, networking, updates and shutdown.

An active controller sends heartbeat messages. Button reads become false after one second without messages. This does not stop actuators by itself: user code must handle the false/disconnected branch with Stop or Off. Only one controller owns the inputs at a time; sequence numbers reject stale messages. The web service is cooperative, not a background thread. Button/connection reads also service it automatically; use remote update in loops without those reads. Avoid long blocking commands while controlling devices live.

25. Remote page layout choice

Choose Button grid or Game D-pad on the page. The browser remembers the layout and custom labels. Button mapping stays fixed: Up=1, Left=2, Right=3, Down=4, A=5, B=6. Switching layout releases held states. Symbols do not assign any motor behavior. Space/Enter operate a focused button; mouse and touch are supported.

26. Remote networking fixes, current driver 1.1.1

The XRP CYW43 hotspot uses WPA2 AES authentication flags (0x400004), replacing an incorrect generic enum value. A previous RemoteControl instance is closed before rebinding port 80 on a subsequent run. Startup prints its driver version, network status and the actual HTTP address.

Join network resets the old station association, supports an empty password for open networks, reports progress every five seconds, and has a 30-second timeout. It distinguishes a rejected password, missing network and general connection failure. Use 2.4 GHz Wi-Fi; a router-assigned address replaces the hotspot address. Captive portal and enterprise login are not implemented.

Latest hardware evidence: the updated driver ran but reported that network Fibre was not found. Join mode is therefore not confirmed working on that network. The user previously reported the remote/upload setup working before testing join mode. This is not evidence of complete hardware validation.

27. Confirmed USB file uploads and module refresh

USB uploads now write UTF-8 data in 256-byte chunks, represented as hex, with a raw-REPL acknowledgement after each command. Data goes to a temporary .upload file. The byte count is checked before renaming it over the destination. Failed driver installation aborts Run/Deploy instead of silently continuing.

After a driver upload, the USB path removes its cached module from sys.modules so the next import loads the new file. RemoteControl's previous listener is closed first. main.py is not treated as an imported driver. This corrected logs where 1.1.1 had uploaded but cached 1.1.0 still ran. Upload acknowledgements remain visible in Console. Bluetooth retains its existing separate binary uploader; these confirmed-write/module-refresh changes apply to USB.

28. OLED scrolling text, library version 2.1.0

New block: OLED scroll [message] on line [1] speed (pixels/sec) [30]. Place it inside a forever loop with a short wait, for example 0.02 seconds. Long text scrolls left, pauses at the ends and repeats. Text that fits stays still. Speed is clamped to 1-120 pixels/second; each line has independent state. The method returns immediately, allowing other loop work to continue. In manual display-update mode, also call OLED update. Static line replacement or Clear resets the corresponding scrolling state. Hardware scrolling remains unverified.

Verification and outstanding work

Current committed tests: tools/test_mecanum.py (7 simulated tests) and tools/test_remote_control.py (8 protocol/network tests). Driver embedding is checked by tools/embed_drivers.py --check. Additional session checks covered Blockly registration and Python generation, all library flyouts, phone-width page rendering, button press/release, D-pad mapping and persistence, real local HTTP requests through the Remote control driver, simulated USB transfers/errors, and OLED scrolling with a stub framebuffer. These do not replace XRP hardware tests.

The previous guide's 913 checks are historical reported results, not a newly rerun suite. The older harnesses are not present in this checkout. Outstanding: join-network testing on a visible 2.4 GHz network, mecanum calibration and hardware validation, OLED scrolling on the display, and Bluetooth driver-update parity. The six legacy expander/NeoPixel files listed in section 3.11 of the guide remain present but unused; they have not been deleted.

Reproduce and use

Use the refreshed source snapshots in XRPBlocks-replication-guide.md together with its new additional-files section. Run python tools/embed_drivers.py, then python tools/embed_drivers.py --check. Start locally with start-xrpblocks.bat or python serve.py; do not open index.html through file://.

For a library update: refresh the IDE, connect USB, then Run or Deploy to upload the new driver. Deploy alone leaves the program stopped. For standalone use, restart after deploying main.py. New libraries are added through Library.

Detailed usage: docs/mecanum.md and docs/remote-control.md. The OLED scroll block tooltip explains loop placement and manual-update behavior.

Changes 14 to 16 are the important structural ones. The PCF8575 and NeoPixel categories from changes 5 and 6 were moved out of the IDE's source and into the new library format, which means the IDE no longer has any built-in knowledge of a specific add-on device.

A2. Change 13: Dark mode

Problem

The pastel theme draws white labels on very pale blocks. Measured against white text, the worst offender is the yellow used by the Board category, at roughly 1.41:1. WCAG 2.1 AA asks for 4.5:1 for normal text. In a bright classroom, or on a projector, several categories are hard to read.

Solution

A light and dark toggle in the toolbar, remembered in the browser so it survives a reload. Light mode is untouched, so nothing a teacher already recognises has moved. Dark mode keeps every category's hue, so blue is still Drive and green is still Sensors, but deepens each colour until white text on it passes 4.5:1.

The same rule is applied automatically to any colour a device library supplies. A library author gives one colour for light mode. If they do not also give a dark one, the IDE darkens theirs in small steps until the contrast test passes, so a library written by a teacher cannot accidentally produce an unreadable category.

A3. Change 14: The device library system

Problem

Changes 5 and 6 added the PCF8575 and NeoPixel categories, and each of them meant touching five files: a block definition file, a generator file, an embedded copy of the MicroPython driver, the toolbox, and the theme. That is a reasonable amount of work for somebody who wrote the IDE and an impossible amount for a teacher who has bought a new sensor.

Solution

A device library is now one JSON file that describes a device: its blocks, the Python each block generates, the category colour and icon, and the MicroPython driver to install on the robot. Nothing in the file is executed. It is data all the way down, which is what makes it safe to email a library to a colleague or fetch one from a web address.

{
  "manifestVersion": 1,
  "id": "pcf8575",
  "name": { "en": "PCF8575 I/O expander", "nl": "PCF8575 I/O-uitbreiding" },
  "category": { "key": "Expander", "colour": "#7E9BD8", "iconSvg": "<svg ...>" },
  "driver":   { "filename": "PCF8575.py", "marker": "PCF8575", "source": "class PCF8575: ..." },
  "instance": { "name": "expander",
                "import": "from PCF8575 import PCF8575, INPUT, OUTPUT",
                "create": "PCF8575()",
                "createConfigured": "PCF8575(address={ADDR})" },
  "blocks":   [ { "type": "xrp_pcf_led",
                  "text": { "en": "PCF8575 LED on pin %1 %2" },
                  "args": [ ... ],
                  "code": "expander.led({PIN}, {STATE})\n" } ],
  "toolbox":  [ { "block": "xrp_pcf_setup" }, { "gap": 16 } ]
}

How it behaves

  • A Library button in the toolbar. Three ways in: the catalogue that ships with the IDE, a file from the computer, or a web address.
  • PCF8575 and NeoPixel no longer appear by default, which gives a beginner a shorter toolbox. What a user adds is remembered and comes back on the next reload.
  • Opening a saved project that uses blocks from a library the browser does not have puts that library back automatically, so work does not silently lose its blocks.
  • A library cannot be removed while its blocks are still in the program. The dialog says so rather than quietly breaking the workspace.
  • Drivers install onto the robot from the manifests, so a device added tomorrow installs its driver with no change to the IDE.
  • A manifest that does not validate is rejected whole, with a list of what is wrong, rather than half-loading and breaking the palette.

The format is documented for somebody else to use in devices/README.md, which is written as a guide rather than as notes to self. Three libraries ship in devices/: the two moved categories and the OLED.

What the format deliberately cannot do. Because a manifest is data and never code, it cannot express a dropdown whose contents change with another field, a block that grows and shrinks, or validation logic beyond what the field types give. A device needing one of those still needs a hand-written block file. Everything the PCF8575 and NeoPixel categories did is expressible, which was the bar the format had to clear.

A4. Changes 15 and 16: The OLED screen library

The first library written from scratch to the published format rather than converted from existing code, and written without touching the IDE's own source. That was the test of whether the format holds. Change 16 then added nine blocks, a picture format and a complete drawing tool, again with no change to the IDE.

The hardware

DisplayModule DM-OLED096-636, a 0.96 inch 128 by 64 monochrome OLED. The controller is a Solomon Systech SSD1315, which takes the same commands as the far more common SSD1306, so the library covers both and works with most cheap 0.96 inch modules. It is an I2C device, so it goes on a Qwiic connector.

DetailValue, and where it came from
Address 0x3C or 0x3D. The datasheet gives 0x78 and 0x7A, which is the 8-bit form including the read/write bit; MicroPython uses 7-bit addresses
Charge pump Command 0x8D with 0x14 for 7.5 V, confirmed against the SSD1315 datasheet rather than assumed from the SSD1306
Text grid Eight lines of sixteen characters, because the driver uses MicroPython's framebuf and its 8 by 8 font
Supply DisplayModule lists the panel at 2.8 V. The usual breakout boards regulate 3.3 V down, but a bare module should be checked against its own datasheet before going on Qwiic

The blocks

Twenty-two, in five groups: setting up; text and numbers; arrows and pictures; drawing; display control; and three reporters.

GroupBlocks
Setting upset up at address, clear
Text and numbers print (console style, scrolls after eight lines), show text on line 1 to 8, show label = value on a line, write text at x and y
Arrows and pictures arrow pointing N degrees, big text at 2x to 6x, show picture at x and y
Drawing pixel, line, rectangle, circle, bar for a sensor reading
Display control update now, update straight away or on command, brightness, normal or inverted, screen on and off
Reportersis connected, screen width, screen height

The compass arrow

The arrow block takes an angle with 0 up, 90 right, 180 down and 270 left, which is exactly what the gyro heading block reports. Plugging the gyro block into the arrow block makes the needle swing as the robot turns, with no arithmetic for the learner to do. It is drawn with a shaft and a solid triangular head, clipped to the screen.

The sketch designer

tools/oled-designer.html is a mouse-driven sketch pad the size of the screen. It opens by double-clicking the file, or at /tools/oled-designer.html when the local server is running. Pencil, eraser, line, rectangle, circle, fill, invert, undo and redo, keyboard shortcuts, canvas sizes from the full screen down to an 8 by 8 sprite, previews at actual size and at double, and grid lines every eight pixels so the character cells and the display's page boundaries are visible.

Copy for XRP Blocks puts a string on the clipboard to paste into the show picture block. The same string can be pasted back into the designer to edit a drawing later. The format is one line of plain text:

XRPI1:128:64:AQD/AP8A/wD/AP8A/wD/AP8A ...

The decoded bytes begin with a mode byte, 0 for raw and 1 for run-length pairs, and the pixels are in the display's own memory layout so they go straight out to the panel. A mostly blank sketch shrinks to about forty characters; a noisy one falls back to raw at about fourteen hundred. Because it is text, it travels in a block, an email or a lesson file with nothing to encode by hand. The driver decodes it without binascii, so there is no dependency to worry about, and caches the decoded copy so redrawing inside a loop costs nothing after the first time.

A missing screen does not stop the robot. Unlike the PCF8575 driver, which raises if the chip does not answer, the OLED driver reports the problem on the console and then quietly does nothing. A robot should keep driving when its screen falls off. The consequence is that a program with no display attached looks exactly like a program that silently failed, so the Console tab is where the difference shows. The OLED is connected block lets a program check for itself.

A5. Change 17: Functions were never generated

This is the most serious defect found so far, and it had been present the whole time.

Problem

The IDE builds the Python by walking outwards from the when program starts block. That is deliberate: it means loose blocks left lying on the canvas are ignored rather than silently becoming part of the program. But a function definition is a loose stack by nature. Nothing connects it to the start block, so the walk never reached it and its body was never generated. The call came out; the definition did not.

oled.clear()
oled.set_auto_show(False)
for count in range(2):
    time.sleep(1)
    UP()          <-- called, but there is no def UP() anywhere in the program
    oled.show()

On the robot that is NameError: name 'UP' isn't defined at the first call, so the program stops before doing anything. Every program using the Functions category was affected, for any device, not only the OLED ones. It presented as "the program runs and nothing happens", because the traceback appears only in the Console tab, which a learner has no particular reason to open.

Solution

A new step in js/app.js generates every function definition on the canvas before the start stack is walked. Their generators put the code into Blockly's definitions table, which is emitted at the top of the program, ahead of everything that calls them.

// A function definition is its own stack on the canvas: nothing reaches it
// from the start block, so walking out from the start block alone never
// generates its body.
this._generateFunctionDefinitions();

code = this._pythonGenerator.blockToCode(startBlock);
code = this._pythonGenerator.finish(code);

Both kinds of function are covered, those that return a value and those that do not.

Worth reporting upstream, alongside the numbers import defect from change 4. If the upstream project generates from the start block in the same way, it has the same defect.

A6. Change 18: The block audit

Every block in the IDE was read against the XRPLib source, not only its documentation, and then exercised in a real browser. Four problems came out of it.

The blink block had never worked

It generated board.led_blink(3, 0.5). XRPLib's led_blink takes one argument, a frequency in Hz, and starts a background timer. Two arguments raise TypeError and the program stops on that line. The block now generates a proper count-and-delay loop, so it does what its label promises and the program waits while it blinks.

The servo was never in degrees

This corrects change 8 in Part One, which described the range as 0 to 200 with 100 at the centre. That was accurate but it was never really an angle. XRPLib's set_angle(d) converts straight to a pulse width, d * 10 + 500 microseconds, so its 0 to 200 is the full 500 to 2500 microsecond travel of a hobby servo. A student with a protractor had no way to make sense of it.

The blocks now take 0 to 180 degrees, mapped across the full travel by one generated helper using degrees * 10 / 9.

The block saysXRPLib receivesPulse width
0 degrees5.6556 microseconds
90 degrees1001500 microseconds, the centre
180 degrees194.42444 microseconds

Five degrees are held back at each end, so a servo is never driven into its own mechanical stop, where it buzzes, draws current and gets hot. The two constants that do this are written at the top of the generated helper, so a class with a servo that can take the full sweep can widen them by hand and see the effect immediately in the Python panel.

def xrp_servo_degrees(servo, degrees):
  SAFE_LOW = 5
  SAFE_HIGH = 175
  if degrees < SAFE_LOW:
    degrees = SAFE_LOW
  elif degrees > SAFE_HIGH:
    degrees = SAFE_HIGH
  servo.set_angle(degrees * 10 / 9)

Centre is now 90 rather than 100, sweep is in degrees and defaults to 0 through 180, and continuous rotation speed stays at -100 to 100 percent, mapped around the 90 degree centre. The change was made in place rather than by adding a second block, so there is one angle block rather than two. A saved project that said 150 meant three quarters of travel and now means 150 degrees, which is a different position. Anything already deployed to a robot as main.py is unaffected.

Effort had three conventions at once

A student could meet "drive straight with 50% effort", "set drive effort 0.5", and a Motors category offering both a 0 to 1 block and a percent block, all in one lesson. Effort is now percent everywhere a student can see, converted and clamped by one helper.

def xrp_effort(percent, lowest=-1):
  effort = percent / 100
  if effort < lowest:
    effort = lowest
  elif effort > 1:
    effort = 1
  return effort

lowest=0 is used for the maximum effort of a measured drive, where a negative value makes no sense. The 0 to 1 motor block stays registered so saved projects still load, but is no longer offered in the toolbox.

Drive effort and arcade were unclamped

The Motors and Servo categories already clamped. drivetrain.set_effort and drivetrain.arcade did not, and XRPLib does not either, so a slip of the keyboard went straight to the motor driver. Both now go through the helper above.

Units were missing where they matter most

drivetrain.set_speed is centimetres per second but motor.set_speed is revolutions per minute, and both blocks simply said "speed". Reflectance returns a decimal from 0 to 1, not a percentage. Every unit-bearing tooltip now names its unit and its range, in English and in Dutch.

Every category reordered

Each category now runs from what a beginner needs down to the advanced, with separators marking each group and a comment in the source saying what each group is for.

CategoryOrder, from the top
